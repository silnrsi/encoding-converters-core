# Handover: EncConverters Modernization

This document is for whoever picks up maintenance or drives the modernization of this repo next. It summarizes what's here, what state it's in, what's actively evolving, and the tradeoffs around the modernization options raised in `CLAUDE.md`. Read `ReadMe.md` first for the architecture overview — this doc assumes it.

## Where things stand

The platform works and is in production use across Paratext, FieldWorks, and various in-house tools. It's ~30 projects, mostly VS2010-era `.csproj` (non-SDK style, `ToolsVersion 12.0`) and native `.vcxproj`/`.vcproj` (one still VS2003/2005-era), held together by:
- A shared strong-name key (`FieldWorks.snk`) and COM self-registration (`RegisterForComInterop`) into `HKLM\SOFTWARE\SIL\...`.
- A hand-rolled plugin discovery mechanism (`EncConverters.InstantiateIEncConverter`) that works around COM's "always resolves to latest GAC version" problem by tracking a specific assembly version per ProgID.
- Bit-width pinning: CC, TECkit, ICU (native), embedded CPython 2.7, `GuesserEC`/`SilFont2Iscii` are all x86/x64-specific native DLLs, which is the hard constraint that rules out `AnyCPU` for the whole solution.

Git history (~800 commits from `bobeaton`/`beaton`/`bob_eaton`, plus `MarkS`, `steve_mcconnel`, `Jim Kornelsen`, `Jason Naylor`, `Bobby de Vos`) shows one person (Bob Eaton) as the primary and effectively sole current maintainer.

## What's actively evolving vs. what's dormant

**Actively developed — `src/EcTranslators`.** Recent commits are almost entirely here: Azure OpenAI API updates, Vertex AI/Gemini model updates, and especially `NllbTranslator` — a self-hosted Meta NLLB translation microservice (Flask + Docker) that just gained support for **private, locally-mounted fine-tuned models** (`daf7e6d`), on top of existing GPU support and per-language-pair fine-tuning. If this repo has a future roadmap, it's here: more model backends, more local/private-model support, and tighter integration with `BackTranslationHelper` (which was recently changed to split-and-translate sentence-by-sentence specifically because NLLB works better that way).

**Stable/maintenance-only — the legacy encoding transducers** (CC, TECkit, ICU, Python, Perl, code-page, Indic/ISCII, AdaptIt guesser). These solve a problem most users have already moved past. Expect occasional bug fixes (e.g. the recent `.Net Regex` `ReplaceWith`-escaping fix) but no new investment. They still need to keep working for existing client apps, but they're a poor place to spend modernization effort beyond what's needed to keep the build green.

**Dormant/incomplete — confirmed, not a priority:**
- `src/ConvertersActivator` — stub only (`ConverterSettings.cs`/`SettingsReader.cs` are empty files); the real feature is described in `Design.txt` but was never finished. It was related to Linux support and was never pursued further. **Decision: leave it in source control as-is; don't invest in finishing it.**
- Linux/autotools build (`configure.ac`, `debian/`, `debian-ec/`, Mono test runner) — **confirmed unused** by any current consumer (or, if anyone still has it, they're content staying on whatever version they already have). It stalled because Mono didn't support some features that were later added elsewhere in the solution, not because Linux support was abandoned on principle. **Decision: safe to stop investing in; not worth actively modernizing right now, but worth revisiting if Mono catches up or another cross-platform .NET runtime approach makes it cheap again** (the `net9.0`/`net9.0-windows` targets in the framework matrix may reopen this door without needing Mono at all).
- `src/CodePageEC/windows/CodePageEC 2010.csproj` — **not referenced by `EncConverters 2019.sln` or any other project, on `master` as well as here** (confirmed via git history — this predates the SDK-style conversion, not something it missed). ReadMe.md still lists `src/CodePageEC` as a live transducer, but nothing currently builds it. **Decision: leave as-is for now** — converting it to SDK-style has no build to validate against; whoever revives this transducer should wire it back into the `.sln` and convert it together, rather than converting it blind.

**Naming fix — confirmed, ready to schedule:** `AIGuesserEC` and `DriveAiEncConverter` have "AI" in their names but predate the AI translation work entirely — "Ai" there stands for **AdaptIt** (a legacy Bible-translation tool), not artificial intelligence. **Decision: rename these to use "AdaptIt" instead of "AI"** (e.g. `AIGuesserEC` → `AdaptItGuesserEC`, `DriveAiEncConverter` → `DriveAdaptItEncConverter`) — confirmed by the project owner, low cost, do it before more people work in this codebase so nobody confuses them with `EcTranslators`.

## The browser-engine problem (GeckoFX now removed)

`CLAUDE.md` calls for deprecating IE and GeckoFX. GeckoFX is done: `WebBrowserGecko.cs`, the bundled `src/EncCnvtrs/Firefox(64)` binaries, and the `installer/FireFox*`/`installer/FireFox64bit` merge modules have all been removed from the repo. `src/EncCnvtrs/WebBrowserAdaptor.cs` now juggles two real engines plus an instructional fallback for the HTML help/config pages used by several transducer setup dialogs (TECkit, compound converters, code-page, `BackTranslationHelper`, etc.):

| Engine | Where | Status |
|---|---|---|
| Internet Explorer (`WebBrowserIE.cs`, WinForms `WebBrowser`) | Windows fallback of last resort | Deprecated engine, per `CLAUDE.md` |
| WebView2/Edge (`WebBrowserEdge.cs`) | Loaded reflectively to avoid Mono crashes | Current Windows default |
| `WebBrowserInstructions.cs` | Shown whenever neither of the above applies — including every non-Windows platform, since `CreateBrowser()` only special-cases IE/Edge on Windows | Not a real browser control — just a `LinkLabel` pointing the user at the Edge WebView2 runtime installer |

Consolidating to WebView2 on Windows is done and is already the default. **The open problem is Linux, and it's now sharper than before GeckoFX was removed:** Linux has no WebView2 equivalent, and with GeckoFX gone it no longer has *any* working embedded-browser option at all — `CreateBrowser()` falls through to `WebBrowserInstructions`, whose message tells the user to install the Microsoft Edge WebView2 runtime, an option that doesn't exist on Linux. That fallback message is now actively wrong for the one platform it's the only remaining option on. Whoever picks this up needs to decide: (a) is Linux UI still needed at all (ties into the "is the Linux build still used" question above), and if so (b) what replaces it — a CEF-based control, a native GTK webview, or at minimum reworking `WebBrowserInstructions`'s message to stop pointing Linux users at a Windows-only runtime.

**Decision, implemented: `AutoConfigDialog`'s "About" tab no longer embeds a browser control.** The "UI" surface in this repo (aside from `MessageBox`es) is essentially just `AutoConfigDialog.cs` and its per-transducer subclasses (one Setup tab each). The only actual use of an embedded browser engine there was the first ("About") tab, which just displays a static instructional HTML page from `redist/Help/*.htm` — confirmed to be plain Word "Save as Web Page" output (`_files` sidecar folders of images, `filelist.xml`, `themedata.thmx`, `.mht` alternates), no forms or scripting. That's disproportionate to the actual need: it doesn't need a full browser engine at all, let alone the two-or-more it was juggling per platform.

Changed `AutoConfigDialog` to launch the Help page in the OS's own default browser (`Process.Start` with `UseShellExecute = true`, pointed at the local `file://`-resolvable path or, for the one subclass that points at a live URL, the URL directly), and removed the "About" tab and the embedded `WebBrowserAdaptor` control from the tab control entirely (`src/EncCnvtrs/AutoConfigDialog.cs`, `AutoConfigDialog.Designer.cs`). The launch is on-request via a new "Help" button next to "Save In Repository" — two earlier cuts of this change both turned out wrong: first it fired automatically on every dialog's construction (an unintended UX regression versus the old silent About-tab content), then it was wired to the dialog's title-bar Help ("?") button (`Form.HelpRequested`), which doesn't work here because that button already has a job — it's a standard WinForms "enter context-help mode, then click a control" affordance driven by the existing per-control `helpProvider.SetHelpString`/`SetShowHelp` calls, and clicking a control that already claims that help handles the request before it ever reaches `Form.HelpRequested`. A plain button avoids the conflict entirely. This is a one-line, zero-dependency, genuinely cross-platform mechanism (`UseShellExecute` maps to the OS shell's file/URL association on Windows, Linux, and macOS alike) — it needed no new package and removes the IE/WebView2 engine choice for this one dialog outright (GeckoFX was already gone by this point).

**Important scoping note — this does not make `AutoConfigDialog` itself cross-platform.** It's still a WinForms `Form`, and WinForms doesn't run on Linux/macOS regardless of target framework (multi-targeting `net9.0-windows` doesn't change that — WinForms is a Windows-only UI stack by design). This change removes a real dependency (no more forced browser-engine choice), but genuine non-Windows support for the dialog itself would still require moving off WinForms entirely (Avalonia, MAUI, etc.) — a separate, much bigger decision, not implied by this one.

**What's now confirmed to remain in scope for `WebBrowserAdaptor`/`WebBrowserIE`/`WebBrowserEdge`:** `TechHindiSiteEncConverter.cs` (`src/SilIndicEncConverters`) still uses `WebBrowserAdaptor.CreateBrowser()` directly — but for a functionally different purpose: it drives a *live* third-party transliteration website in-process (navigates to it, executes JS against form elements) rather than displaying static local docs. That's a real, different requirement (interactive automation of a live page), not solvable by just shelling out to a browser, so the browser-engine abstraction and its remaining implementations stay as-is for that one consumer. The Linux browser-engine question above is still open, but its blast radius already shrank to this single consumer instead of every transducer's Setup dialog — and is now more urgent for that consumer specifically, since Linux has no working in-process option left at all.

## Generic subprocess fallback for host-process conflicts

Investigating a live `TechHindiSiteEncConverter` bug (`Unable to cast to Microsoft.Web.WebView2.Core.Raw.ICoreWebView2Environment` when run inside Word) turned up a well-documented WebView2 failure mode ([WebView2Feedback#2870](https://github.com/MicrosoftEdge/WebView2Feedback/issues/2870)) that has nothing to do with SDK/runtime version skew: Windows' DLL search order reuses an *already-loaded* module with the same filename regardless of directory, so if `WINWORD.EXE` already has its own `WebView2Loader.dll` resident (Word has shipped WebView2-based UI for years), our own bundled copy never gets a chance to load. No amount of bumping `Microsoft.Web.WebView2` (see `EncCnvtrs 2010.csproj`) fixes this.

This isn't a one-off. The project owner has hit the same *category* of problem before, in a different guise: installing `SILConverters` on a machine that already has Paratext (which bundles its own, often-outdated copy of the EncConverters core) means the new SILConverters features never show up until someone manually replaces `SilEncConverters40.dll` etc. in Paratext's install folder — a hack that only works because `IEncConverter` hasn't broken compatibility across those versions. Both cases are the same underlying pattern: **a host process (Word, Paratext, or any future client) can have its own version of something our plugin also needs, already resident, with no way to win that race in-process.**

**Proposed fix — a generic, engine-agnostic subprocess fallback**, detecting when running in-process is unsafe and instead running the conversion in a fresh, isolated process that starts with nothing pre-loaded:

- **Detection is proactive, not reactive, on purpose.** A native ABI mismatch can in the worst case crash the host process outright (an access violation, not a catchable .NET exception) — so the design leads with a check performed *before* touching the risky resource: walk `Process.GetCurrentProcess().Modules` for a named native dependency (e.g. `WebView2Loader.dll`); if a copy is already resident from a directory other than our own, it's unsafe to initialize in-process. This scan runs on every instantiation, in every process — never skipped or shortcut by the cache below, because the same `TechHindiSiteEncConverter` running outside Word (a different host, nothing pre-loaded) legitimately works fine in-process, and nothing should misapply a Word-specific failure somewhere that never had the conflict. A reactive catch-and-remember pass (see the caching note below) exists as a secondary net for the failure modes that *do* throw cleanly instead of crashing — which is exactly what the `WebBrowserEdge.cs` fix (surfacing `CoreWebView2InitializationCompletedEventArgs.InitializationException` instead of swallowing it) now makes possible.
- **Where a converter declares the risk**: a new `protected virtual IEnumerable<string> RiskyNativeDependencies => Enumerable.Empty<string>();` on the abstract `EncConverter` base class (`src/EncCnvtrs/EncConverter.cs`), not a new member on the public `IEncConverter` COM interface (`src/ECInterfaces/ECInterfaces.cs`). Every real transducer type derives from `EncConverter`; none implement `IEncConverter` from bare metal. This keeps the versioned 4.0 COM contract that external consumers (Word VBA/VBScript macros doing `CreateObject()`) depend on completely untouched. If that assumption ever breaks, the fallback is a versioned sibling interface (`IEncConverterRiskyDependencies`, checked via `is`/`as`) — the same numbered-interface convention WebView2's own SDK uses (`ICoreWebView2Environment`, `...2`, `...10`, ...) for exactly this kind of additive, non-breaking capability.
- **Decision point**: `EncConverters.AddEx` (`src/EncCnvtrs/EncConverters.cs`) already separates "construct via `InstantiateIEncConverter`" from "call `.Initialize(...)`" as two steps. The check slots in between: construct the real instance (cheap and side-effect-free — native work happens in `Initialize`/`PreConvert`/`DoConvert`, not the constructor), read `RiskyNativeDependencies` off it, and only call `Initialize` if nothing conflicts; otherwise discard it and hand back a subprocess-backed proxy built from the same ProgID/assembly/spec tuple instead.
- **Compound converters are covered for free.** `CmpdEncConverter`/`FallbackEncConverter` (`src/EncCnvtrs/CmpdEncConverter.cs`, `FallbackEncConverter.cs`) never instantiate their own steps — they're handed already-resolved `IEncConverter` references and only ever call interface methods on them. Whether a given step is the real in-process object or a subprocess proxy is invisible to them.
- **Caching, scoped per host to avoid false positives.** Reuse the existing `SEC_ROOT_KEY` (`SOFTWARE\SIL\SilEncConverters40`) registry convention already used for small flags like `UseEdge`/`ShowToolTips` (`src/EncCnvtrs/EncConverters.cs`) — HKCU-overrides-HKLM, best-effort writes wrapped in try/catch. The cache key is `(host process name, ProgID)`, not just `(ProgID)`: a converter flagged bad inside `WINWORD.EXE` has zero effect on the same converter running inside Paratext, a test harness, or anything else — each host gets its own independent verdict. The cache is only a shortcut for the *reactive* path — once a given host+converter combination has thrown a recognized conflict signature once, skip straight to the subprocess route for that combination next time, rather than re-risking the crash-prone path on every conversion call.
- **The generic subprocess host** (see below, first slice already built): unlike `AzureOpenAiExe`/`VertexAiExe` (which reimplement their vendor-API calls directly and never touch `IEncConverter` at all), this one is genuinely engine-agnostic because it drives the *same* `Activator.CreateInstance(assemblyFullName, progId)` → `Initialize(...)` → `Convert(string)` sequence `InstantiateIEncConverter` already uses (`EncConverters.cs:2401-2480`) — proven to work standalone with zero dependency on the `EncConverters` dispatcher/repository (`src/TestEncCnvtrs/TestIcuTranslit.cs:64-73` already does exactly this against a concrete type). It needs no engine-specific knowledge, just the `Initialize` parameters plus the input text, serialized as JSON.
- **Finding the one canonical copy of the host exe.** Whatever process detects the conflict must defer to a *single* installed copy, not each carry a private one, or different hosts on the same machine could disagree about the fallback that's supposed to be authoritative. The obvious existing candidate — `SOFTWARE\SIL\SilEncConverters40\Installer\InstallerPath` (`EncConverters.cs:40-41`) — turns out to be the wrong mechanism: it's a last-installer-wins pointer to wherever the *core* assembly itself was most recently installed (which could be Paratext's own private, possibly-stale bundle), not a stable pointer to a specific product's location. This needs a new, distinct value — e.g. `HKLM\SOFTWARE\SIL\SILConverters` value `InstallDir` — written only by the SILConverters product installer (the one guaranteed to actually contain the host exe). If that key is absent (no SILConverters product on the machine at all — bare Paratext-only, say), there's no safe fallback available; the design should degrade gracefully by proceeding with the risky in-process attempt anyway (no worse than today) rather than hard-failing.
- **Packaging deliberately excludes the core module.** The host exe must not be installed for every consumer of the bare EncConverters core (e.g. Paratext-style installs that only take `EC_40_MM`/`EC_40_64bit_MM`) — it's SILConverters-specific infrastructure. Plan: a new, dedicated pair of merge modules (`EncConverterHostExeMM`/`EncConverterHostExe64bitMM`, matching `EcTranslatorsMM`'s existing structure) that only `silconverters`'s own top-level installer references and that writes the new `InstallDir` value — `EC_40_MM` and every other existing module stay untouched.

**Optional keep-alive: reusing one subprocess across many `Convert()` calls, instead of spawning fresh every time.** A caller driving a heavy-init converter (an AdaptIt KB load, a cloud translator SDK client bootstrap, spinning up ICU) through the host exe many times in a loop shouldn't re-pay full `Initialize()` cost on every single string. Worth being explicit about what prompted checking this at all: the project owner's own impression was that `AzureOpenAiExe`/`VertexAiExe` already stay resident across calls — confirmed false by reading the code. `ExeEncConverter.DoExeCall` (`src/EncCnvtrs/ExeEncConverter.cs`) calls `Process.Start` fresh on *every* `Convert()`, and the default `WriteToExeInputStream` closes stdin right after writing one line — so even though those exes' own `Program.cs` has a `while` loop over stdin that looks built for multiple lines per run, the parent never actually exercises it; one process, one round-trip, exit, every time. Nothing in this repo — not that pattern, not `EncConverterHostExe` as first built — keeps a process alive across calls today.

- **Opt-in, fully backward compatible.** Two new fields on `EncConverterHostRequest`: `KeepAliveSeconds` (default `0`) and `SessionPipeName`. `0`/unset is byte-for-byte today's one-shot behavior — no existing caller needs to change anything. A positive value means: after answering the first `Convert()` call exactly as today, stay resident and serve further calls over a named pipe against the *same* already-initialized `IEncConverter` instance, self-terminating if idle too long.
- **Two deadlocks found along the way, the second only by actually running it.** Just writing the first result to stdout and *not* exiting would hang every existing caller, because `Process.StandardOutput.ReadToEnd()` (the read pattern `TestEncConverterHost.RunEncConverterHostExe` and presumably any future caller uses) doesn't return on "output is available" — it returns on EOF, which for a redirected pipe only happens when the write handle closes. The seemingly obvious fix — after writing and flushing the first result, close `Console.Out`/`Console.Error` before entering the pipe loop — turned out to be a second, subtler dead end: confirmed empirically (the first cut of `TestEncConverterHostKeepAlive` hung for *exactly* `KeepAliveSeconds` before "succeeding," a dead giveaway) that closing .NET's `Console.Out` does **not** reliably close the underlying OS pipe handle while the process itself keeps running — so the caller's `ReadToEnd()` only ever unblocks once the whole process actually exits, which defeats the entire point. The actual fix: **nothing is ever written to stdout in keep-alive mode at all.** The caller connects to the pipe for every conversion, including the first one — `EncConverterHostRequest.InputText` is simply ignored when `KeepAliveSeconds > 0`. Simpler than trying to preserve "the first call looks like the one-shot path" as a special case, and it sidesteps the unreliable-EOF problem entirely rather than working around it.
- **The pipe protocol.** `SessionPipeName` is a GUID the *caller* generates before launching (no discovery round-trip needed). The child opens a `NamedPipeServerStream(..., PipeTransmissionMode.Message)` — Message mode gives multi-request/response framing for free, no hand-rolled length-prefixing needed — and loops: read one `EncConverterHostPipeRequest` (input text + optional per-call `DirectionForward`/`NormalizeOutput` overrides, or a `Shutdown` flag for a clean voluntary exit), call `Convert()` again on the same instance, write one `EncConverterHostPipeResponse` (`Success`/`Result`/`ErrorMessage`, plus `ServerProcessId` specifically so a caller or test can prove the *same* process answered every call rather than inferring it from timing). Gotcha worth remembering: `NamedPipeClientStream` does not inherit `PipeTransmissionMode.Message` from the server automatically — a client must set `ReadMode = PipeTransmissionMode.Message` itself after `Connect()`.
- **Self-terminating, not parent-dependent.** A `System.Threading.Timer` resets on every message *received* (not after `Convert()` finishes, so a slow conversion is never mistaken for idle time) and hard-exits (see below) if it fires — so an orphaned child (parent crashed, forgot to clean up, whatever) doesn't run forever regardless of what the parent does or doesn't do. `IEncConverter` has no `Dispose`/cleanup member (checked — `src/ECInterfaces/ECInterfaces.cs`), so this needs no graceful converter teardown step.
- **A third deadlock, found later, only by running the Python3 converter specifically: `Environment.Exit`/a bare `return` from `Main` can hang forever too, and it's not this codebase's bug.** `TestPy3ScriptEncConverter_ViaSubprocess` (which works fine under `net462`/`net48`) hung indefinitely under `net9.0-windows` specifically, even in a fully standalone repro with no test host involved at all. Root-caused with `dotnet-dump collect` + `clrstack`: the *finalizer thread* was stuck inside `Python.Runtime.PythonEngine.OnProcessExit` → `PythonEngine.Shutdown()` → `Py.GIL()` → `PyGILState_Ensure()`, permanently waiting to reacquire the Python GIL. Python.NET (the `pythonnet` package `PyScriptEC`/`Py3ScriptEncConverter` uses) registers an `AppDomain.ProcessExit` handler to shut Python down gracefully — and that handler deadlocks, at least under whatever GIL state a `Convert()` call leaves things in here. Critically, **this fires (and blocks on) regardless of whether the process ends via a bare `return` from `Main` or an explicit `Environment.Exit()` call** — switching the one-shot exit path to `Environment.Exit()` (an earlier cut of the fix for the Main/net9.0-windows-hang investigation below) did not help, because `ProcessExit` fires either way. The reason it never surfaced under `net462`/`net48`: **.NET Framework enforces roughly a 2-second timeout on `ProcessExit` handlers before forcibly continuing shutdown anyway; modern .NET (Core/5+) removed that timeout and waits indefinitely.** So this Python.NET deadlock was always latent — Framework was just silently papering over it every single time by timing out and killing the process regardless, and nobody had run the Python3-via-subprocess test specifically under `net9.0-windows` until now to notice. **Fix**: every exit path out of `Program.Main` (including the keep-alive idle-timeout callback) now goes through a `HardExit(exitCode)` helper that P/Invokes `TerminateProcess` directly on the current process, bypassing `AppDomain.ProcessExit`/finalizers/all managed shutdown machinery entirely — chosen over `Process.Kill()` specifically because `Kill()` can't set a specific exit code, and this protocol's whole success/failure signaling depends on exit code 0 meaning success. This isn't a Python-specific workaround — bypassing `ProcessExit` is the right general policy for this exe regardless of *which* converter's native library might misbehave on shutdown, since the process has no state worth an orderly teardown for anyway (same "`IEncConverter` has no `Dispose`" fact noted above). Verified via a live `dotnet-dump` capture showing the hang, then confirming a clean ~0.3–1.7s exit with the correct exit code after the fix, both standalone and through the actual NUnit test, on both `net9.0-windows` platforms (x86/x64). **Side effect of the switch to a true hard kill, caught by a flaky test rerun, not a real bug**: `TestSubprocessFallback.Convert_BadProgId_ThrowsRatherThanHangingOrSucceeding` occasionally got `IOException: Pipe is broken` instead of the expected `TimeoutException` — `TerminateProcess` can tear down the child's named pipe object at any point mid-connection-attempt, so the client occasionally sees "briefly connectable, then broken" instead of a clean "never available" (confirmed non-deterministic: reran the exact same test and got the expected exception the very next time). The test's assertion was broadened to accept either exception type, matching what it actually cares about (fails loudly and promptly, never hangs, never silently succeeds) rather than which specific exception reports that.
- **Windows-only** (`PipeTransmissionMode.Message` is a Windows-only mode in .NET) — consistent with this whole subsystem already being Windows-only (WinForms/WebView2/Word/Paratext hosts).
- **Job Object hardening — built and verified this pass.** `HostProcessJobObject` (`src/EncCnvtrs/HostProcessJobObject.cs`) closes the gap the self-timeout alone can't: if the *host* process itself (Word, Paratext) terminates uncleanly — a crash, or being force-killed — no managed code runs at all, so no `Dispose()`/finalizer/`AppDomain.ProcessExit` handler can be relied on to send the graceful `Shutdown` message, and the child would otherwise sit around for up to its full idle timeout as an orphan. The fix is deliberately *not* tied to any .NET object's lifetime (that's exactly the unreliable thing it exists to route around) — it's a Windows Job Object, a kernel construct tied to the *process handle table* instead: `PersistentEncConverterHostSession.EnsureSessionStarted` calls `HostProcessJobObject.AssignToKillOnCloseJob` right after `Process.Start`, which lazily creates one job (shared across every session in the process — Windows allows multiple processes in one job, no need for one job per session) with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` set, and assigns the child to it. The job handle is deliberately never explicitly closed — it's meant to live exactly as long as this process does, and get closed *by the OS* (along with the rest of this process's handle table) whenever this process itself terminates, for any reason. Because of the kill-on-close flag, the instant that handle closes, Windows automatically terminates every process still assigned to the job.
  **Verified for real, not just by code review**: `TestHostProcessJobObject.LaunchSessionAndBlock_ForExternalCrashKillVerification` (`[Explicit]` — it deliberately gets its own host process hard-killed mid-run, never something a normal test pass should do to itself) launches a real keep-alive session, proves the child converted correctly, then blocks for 10 minutes. Ran it manually via `dotnet test --filter`, located the spawned `EncConverterHostExe.exe`'s actual parent process (`testhost.exe`, found via `Get-CimInstance Win32_Process`, not assumed by name), then hard-killed that parent via `Stop-Process -Force` (a `TerminateProcess`-equivalent, no managed shutdown code runs) and timed how long the child survived. **Result: the child terminated 0.0075 seconds after the parent was killed** — not anywhere near the 10-minute idle timeout that would otherwise apply, conclusively confirming the OS-level kill-on-close mechanism is what actually took it down.

**Detection/wiring machinery — built this pass.** All of Part 1's previously-design-only pieces now exist and are wired together:
- `EncConverter.RiskyNativeDependencies` (`src/EncCnvtrs/EncConverter.cs`) — the virtual property described above. `TechHindiSiteEncConverter` (`src/SilIndicEncConverters/TechHindiSiteEncConverter.cs`) overrides it with `base.RiskyNativeDependencies.Concat(new[] { "WebView2Loader.dll" })`, the only converter that declares a risk in code so far.
- **Post-deployment escape hatch, no rebuild required.** The base class's default implementation doesn't just return empty — it reads `Properties.Settings.Default.AdditionalRiskyNativeDependencies` (`src/EncCnvtrs/Properties/Settings.settings`/`Settings.Designer.cs`), a new application-scoped `StringCollection` setting, empty by default, following the exact existing pattern this project already uses for `RegexNetLettersToUnescape`. If a new risky DLL turns up in the field that no `EncConverter` subclass declared in code (missed during testing, a transducer type added later, whatever), an admin can add a `<string>SomeNewDll.dll</string>` entry to this setting's `<value>` in the installed `*.config` file and every converter type picks it up immediately — `TechHindiSiteEncConverter`'s override (and any future subclass override) is written as `base.RiskyNativeDependencies.Concat(...)` specifically so it *merges with*, rather than replaces, this config-sourced list. **Caveat worth knowing before relying on this in the field**: .NET Framework's `ApplicationSettingsBase` resolves application-scoped settings against the *entry executable's* own `.config` file (`AppDomain.CurrentDomain.SetupInformation.ConfigurationFile`), not the config file sitting next to `SilEncConverters40.dll` itself — for a COM add-in loaded inside Word, that means editing `WINWORD.EXE.config` (in Word's own install directory), not anything shipped alongside this assembly's plugin folder. This is standard .NET Framework/COM-interop behavior, not specific to this feature (the existing `RegexNetLettersToUnescape` setting already has the exact same characteristic), but it means each host application that needs the escape hatch needs its own edit to its own `.config` file.
- `NativeModuleConflictDetector.IsLoadedFromElsewhere` (`src/EncCnvtrs/NativeModuleConflictDetector.cs`) — the module-scan utility, exactly as designed: walks `Process.GetCurrentProcess().Modules`, compares the target filename case-insensitively, and reports a conflict only if a match is found loaded from a directory other than the one passed in (not loaded at all, or loaded from our own directory, are both "safe").
- `EncConverters.FindEncConverterHostExePath`/`IsKnownToNeedSubprocessFallback`/`RememberNeedsSubprocessFallback` (`src/EncCnvtrs/EncConverters.cs`) — the `InstallDir`-based discovery (read-only; see the packaging note below for what's still missing) and the per-host-process registry cache, both built exactly per the design (HKCU-overrides-HKLM via the existing `GetRegistryValue` helper; best-effort try/catch writes mirroring the `UseEdge`/`ShowToolTips` convention).
- `SubprocessEncConverter` (`src/EncCnvtrs/SubprocessEncConverter.cs`) — the proxy `AddEx` hands back. Implements `IEncConverter` directly rather than deriving from `EncConverter`: the base class's `Convert`/`ConvertEx` machinery (`InternalConvertEx`/`PreConvert`/`DoConvert`) operates on raw byte buffers and per-engine `EncodingForm` decisions that only make sense for a converter actually doing the conversion itself, and this proxy never does — it forwards a wide string to the real converter running in the child (which goes through that exact machinery there, correctly) and returns whatever comes back. `ConvertToUnicode`/`ConvertFromUnicode` are implemented as simple code-page-based widen/narrow around `Convert()` rather than round-tripping raw bytes through the subprocess — sufficient for every currently-risky converter (`TechHindiSiteEncConverter` is Unicode-to-Unicode, so these paths would just throw `InvalidConversionType` for it anyway, matching what the real converter would do). Backed by `PersistentEncConverterHostSession` (`src/EncCnvtrs/PersistentEncConverterHostSession.cs`) — the caller-side keep-alive session class flagged as not-yet-built at the end of the previous pass, now built: launches `EncConverterHostExe.exe` in keep-alive mode with a generous default idle timeout (10 minutes — a host-app editing session doing occasional conversions shouldn't have its subprocess reaped between keystrokes), and transparently relaunches-and-retries once if a `Convert()` call finds the pipe broken (e.g. the previous session's idle timer already fired).
- `EncConverters.AddEx` (`src/EncCnvtrs/EncConverters.cs`) — the choke-point wiring, exactly at the seam the design identified (between constructing the real instance and calling `Initialize`). Both nets are live: **proactive** — if the constructed instance declares any `RiskyNativeDependencies`, and an `InstallDir`-discovered host exe exists, check the per-host registry cache and the module scan *before* ever calling `Initialize`; on a hit, construct `SubprocessEncConverter` instead and initialize that. **Reactive** — if nothing was proactively detected but `Initialize()` still throws (and the converter did declare a risk, and a host exe is available), remember the failure in the registry cache and retry once via the proxy before giving up. If no `InstallDir` is configured at all, both nets are skipped entirely and the code behaves exactly as it did before this feature existed (degrade gracefully, per the design).
- **A real blind spot found only by testing on a clean VM with the actual Word/WebView2 collision: `AddEx`'s two nets both only guard `Initialize()`, but `TechHindiSiteEncConverter` never touches WebView2Loader.dll there at all.** Its browser control is created lazily, inside `PreConvert` (fired on the *first `Convert()` call*, not `Initialize()`) — confirmed by reading the code, not assumed. So at `Initialize()` time nothing has loaded the DLL yet (the proactive scan correctly sees "not loaded" and lets the real converter through), `Initialize()` itself is just string parsing (nothing for the reactive catch to catch), and only the *first real conversion* actually triggers the collision — by which point `AddEx` is long done and has no visibility into subsequent `Convert()` calls on the instance it already handed back. This meant the exact converter that motivated the whole feature was the one case the original wiring couldn't catch at all, and it's why the fallback wasn't engaging on the VM even with everything else (install, registry, host exe) correctly in place.
  **Fix — a third layer, in `EncConverter` itself (`src/EncCnvtrs/EncConverter.cs`), not `AddEx`:** a `protected bool WasJustLoaded = true` field, and a private `SubprocessEncConverter _fallbackProxy` field, plus:
  - `Convert()`/`ConvertEx()` now try the real in-process path first, and on *any* exception from a converter that declared a risk, engage the fallback (`EngageSubprocessFallback()`: writes the registry cache, builds a `SubprocessEncConverter` from this instance's own already-stored `Initialize()` parameters — `LeftEncodingID`/`RightEncodingID`/`ConversionType`/`ProcessType`/`CodePageInput`/`CodePageOutput` are already sitting on the base class, no need to have captured them separately) and **retry the exact same call through it, within the same method call** — self-healing on the very first failure, not just from the next launch onward, which is strictly better than what `AddEx`'s own reactive net can do (it can only ever affect the *next* `Initialize()`, since by the time it would catch anything the caller already holds a reference to this exact instance). Once `_fallbackProxy` is set, every later call on this instance goes straight to it — the doomed in-process path is never retried.
  - `PreConvert` (base) checks `WasJustLoaded` once (then clears it) and runs the proactive module scan *after* whatever lazy-load logic a subclass's own `PreConvert` override already ran — this is deliberately a *secondary*, weaker check (it can't help the call that just happened if that load already threw; `Convert()`/`ConvertEx()`'s catch above is what actually does that) but does catch the case where a load technically "succeeds" while still leaving a foreign, untrusted copy of a declared-risky dependency resident, engaging the fallback for every later call even though nothing threw this time.
  - `TechHindiSiteEncConverter.PreConvert` needed exactly one change to participate: move its own `Load()` call *before* `base.PreConvert(...)` instead of after (the ordering nearly every other `PreConvert` override already uses stays untouched — only a converter that both declares a risk *and* has a lazy load step needs this, which today is only this one). No try/catch needed in the subclass itself: `Convert()`/`ConvertEx()`'s catch, one level up, already covers any exception from anywhere inside the `PreConvert`/`DoConvert` pipeline, wherever it actually originates.
  Verified with a purpose-built `AlwaysRiskyTestEncConverter` (`src/TestEncCnvtrs/AlwaysRiskyTestEncConverter.cs` — declares a risk and throws on every in-process attempt, succeeds only when it detects it's running as `EncConverterHostExe.exe`, the same "works fresh, fails in this process" shape as the real bug without needing an actual native DLL collision to reproduce): `TestSubprocessFallback.Convert_SelfHealsOnFirstFailure_WhenRiskyConverterThrowsInProcess` calls `Convert()` once and gets the correct result back with zero visible failure, then calls it again and confirms the second call also succeeds (via the now-cached proxy, without re-attempting the in-process path). Full suite re-run clean on both platforms afterward.

### The Edge/WebView2 hang, re-investigated: a genuine, unrecoverable native failure mode — and why the fix is routing around it, not curing it

Re-enabling the previously-commented-out Edge test case (`TestTechHindiSiteConverter(...;Edge)`, disabled since before this session with the comment "Edge fails due to an incompatibility... with Outlook") reproduced a real, indefinite hang inside `WebBrowserEdge.Initialize()`, confirmed on both this dev machine and the project owner's clean test VM — not a leftover-process or Outlook-specific artifact (both explicitly ruled out below). Chasing this down turned up several distinct, real bugs, some inside this feature's own new subprocess machinery, on top of the original hang. In order:

- **First hypothesis, tested and ruled out: ~40 leaked `msedgewebview2.exe` helper processes accumulated from repeated test runs across the session.** Killing all of them and re-running the Edge test in a freshly-cleaned environment reproduced the *exact same* failure — proving the leak (real, and worth its own fix eventually — nothing in this codebase ever calls `Dispose()` on a `WebBrowserAdaptor`/`WebView2` control today, success or failure) was a confound, not the root cause.
- **Second hypothesis, tested and ruled out: contention with Outlook's own WebView2 usage**, per the original disabling comment. `tasklist` confirmed neither Outlook, Word, nor a standalone `msedge.exe` was running at all during the reproduction — so whatever the original comment's author hit, it isn't *currently* about live cross-process contention, at least not in this exact reproduction.
- **A live `dotnet-dump` capture (from the previous pass) already established the actual shape of the hang**: a thread genuinely stuck forever inside `ICoreWebView2Environment.CreateCoreWebView2Controller`'s native COM call, with no fault, no completion event, nothing else to ever observe — not something any amount of additional `await`/event-wiring on the .NET side can detect or cancel, because the underlying Task itself never reaches a terminal state.
- **Adding a bounded timeout (`WebBrowserEdge.WebView2InitializationTimeoutSeconds`, 20s) converts the hang into a bounded failure, but abandoning the stuck operation — via `Dispose()`, per WebView2's own documented cancellation contract, or by doing nothing at all and just walking away — reliably crashes the *entire host process* a few seconds later** with a native, uncatchable Chromium-internal error: `[ui\gfx\win\window_impl.cc:172] Failed to unregister class Chrome_WidgetWin_0. Error = 1411` (`ERROR_CLASS_HAS_WINDOWS`). Confirmed via direct, isolated reproduction (a hand-built request JSON run straight through `EncConverterHostExe.exe`, no test framework involved) that this happens identically whether or not `Dispose()` is called first — meaning **once this specific native operation gets stuck, there is no safe way to abandon it from managed code at all**; the eventual crash is not something a `try`/`catch`, a timeout, or a `Dispose()` call can prevent, only relocate.
- **A genuinely separate, real bug found along the way and fixed: `EncConverterHostExe.exe` was missing `[STAThread]` on `Main`.** A plain console app's `Main` defaults to MTA with no attribute; WebView2 requires an STA apartment. Direct, isolated invocation against a WebView2-based request failed immediately (not a hang) with `System.Runtime.InteropServices.COMException: Cannot change thread mode after it is set. (0x80010106 (RPC_E_CHANGED_MODE))` — WebView2's own attempt to establish STA lost the race against whatever implicitly initializes MTA first in a bare console app. Fixed by adding `[STAThread]` to `Program.Main` (`src/EncConverterHostExe/Program.cs`) — harmless for every other converter type, which don't care about apartment state at all, and a real, standalone correctness fix independent of everything else here (any future WebView2-touching converter run through this host would have hit the identical failure).

**Given the hang is real, reproducible in complete isolation, and not something managed code can safely abandon once entered, the fix is architectural, not a retry/timeout tweak: keep WebView2 out of the real host process's own address space entirely whenever a subprocess route is available, rather than trying to survive an in-process failure that can crash the host regardless of how it's caught.** This is a new, third layer on top of the two already documented above (the module-scan/registry-cache net, and `EncConverter.Convert()`'s catch-and-retry): a **proactive, unconditional-for-Edge** reroute, added because the other two layers both assume a risky operation either fails cleanly or doesn't run at all — neither holds here, since the operation can succeed at first, then poison the process later with no exception ever thrown at all.

- **`TechHindiSiteEncConverter.PreConvert`** (`src/SilIndicEncConverters/TechHindiSiteEncConverter.cs`) now checks a new `WillUseEdgeBrowser` property (mirrors `WebBrowserAdaptor.CreateBrowser`'s own `WhichBrowser.Undefined` resolution logic, without constructing anything) *before* ever calling `Load()`. If it would resolve to Edge, and a subprocess route is actually available (`EncConverters.IsSubprocessFallbackAvailable`), and this code isn't already running inside the subprocess host itself (`EncConverters.IsRunningAsSubprocessHost` — see below), it calls the now-`protected` `EngageSubprocessFallback()` directly and then *throws* a lightweight `ApplicationException` to unwind out of `PreConvert`/`InternalConvertEx` before `DoConvert` ever runs against a `_webBrowser` that `Load()` was never given the chance to create. `EncConverter.Convert()`/`ConvertEx()`'s own existing catch-and-retry (unchanged) is what actually catches this and retries via `_fallbackProxy` — no new retry logic needed, this just makes sure the *first* attempt never touches WebView2 in-process at all when there's somewhere safer to run it.
- **Recursion guard, needed because of the above: `EncConverters.IsRunningAsSubprocessHost`** (new, public — `Process.GetCurrentProcess().ProcessName` compared against `EncConverterHostExe`) is checked both by `TechHindiSiteEncConverter`'s proactive reroute (skip it — this *is* the one place it's actually safe to attempt Edge for real) and, as a hard backstop, inside `EncConverter.EngageSubprocessFallback()` itself (now `protected`, was `private` — returns `false` immediately if already running as the subprocess host, rather than trying to delegate to a fallback that would just recurse into launching another copy of itself forever).
- **Also added, for the same reason**: `EncConverters.IsSubprocessFallbackAvailable` (new, public — thin wrapper over the existing `FindEncConverterHostExePath() != null` check), so a converter can gate a *proactive* reroute on "is there actually somewhere to send this" without needing `internal` access to the underlying registry-lookup method from a different assembly (`TechHindiSiteEncConverter` lives in `SilIndicEncConverters40.dll`, not `SilEncConverters40.dll`).

**A second, distinct, pre-existing bug surfaced only once this proactive path made the subprocess-fallback registry cache get populated for real for the first time**: once *any* `TechHindiSiteEncConverter` instance in a given host process engages the fallback, `EncConverters.AddEx`'s own registry-cache check (`IsKnownToNeedSubprocessFallback`, keyed by `(host process name, ProgID)` — by design, coarser than per-spec/per-browser-choice) correctly starts routing *every subsequent* `TechHindiSiteEncConverter` instantiation in that same host straight to `SubprocessEncConverter`, *before* the real converter's own `Initialize()` (and its `MakeUniDirectional` adjustment for specs with no reverse function) ever runs. Since `SubprocessEncConverter`'s `_conversionType` was only ever set from whatever the *caller* originally passed in, this left the proxy stuck reporting the original, pre-adjustment (bidirectional) `ConversionType` forever — surfaced as a real regression in `TestTechHindiSiteConverter("...;InternetExplorer")` (a spec with no reverse function, previously never actually exercising this code path because the registry cache had never been meaningfully populated for this ProgID before): `System.ApplicationException: ... The configured conversion type (Unicode vs. non-Unicode) is invalid for this converter`, thrown because the test's own `IsUnidirectional(theEc.ConversionType)` check saw the stale bidirectional value and attempted a reverse conversion the real (child-side) converter had already correctly locked out.

- **Fix: a one-time "handshake" response**, sent by `EncConverterHostExe`'s `RunKeepAliveLoop` (`src/EncConverterHostExe/Program.cs`) immediately after accepting the pipe connection and *before* any conversion request, reporting back whatever the real converter's own `Initialize()` adjusted — `LeftEncodingID`/`RightEncodingID`/`ConversionType`/`ProcessType` — via four new nullable `Adjusted*` fields on `EncConverterHostPipeResponse` (`src/EncConverterHostExe/EncConverterHostPipeMessage.cs`). `PersistentEncConverterHostSession.EnsureSessionStarted` (`src/EncCnvtrs/PersistentEncConverterHostSession.cs`) consumes this handshake right after connecting and exposes the adjusted values as properties; `SubprocessEncConverter.Convert`/`ConvertEx` (`src/EncCnvtrs/SubprocessEncConverter.cs`) adopt them onto its own fields after every call via a new `AdoptAdjustedValuesFromSession()` — so by the time a caller checks `ConversionType` after at least one real conversion has gone through (exactly the sequence `TestTechHindiSiteConverter` itself follows: two forward `Convert()` calls, *then* the `IsUnidirectional` check), it reflects the real, adjusted value rather than the caller's original guess. Deliberately **not** made eager (i.e. `SubprocessEncConverter.Initialize()` still doesn't force a session launch) to avoid turning every `AddEx`-time instantiation of a known-risky converter into an immediate subprocess-launch cost — the existing lazy-launch-on-first-`Convert()` behavior is unchanged; only what happens once a session *does* start changed.
- **A raw-protocol test needed updating for the same reason**: `TestEncConverterHostKeepAlive.TestKeepAliveSession_ReusesSameProcessAcrossCalls` (`src/TestEncCnvtrs/TestEncConverterHostKeepAlive.cs`) drives the pipe protocol directly (not through `PersistentEncConverterHostSession`) to prove session reuse — it needed one added line to consume the same handshake message before sending its first real request, or every response it read was one message behind where it thought it was, eventually breaking the pipe. `TestKeepAliveSession_SelfTerminatesWhenIdle` was unaffected (it never connects a client at all).

**A third, independent bug, found by testing the *isolation* the subprocess design is supposed to provide, not just the WebView2 hang itself: `PersistentEncConverterHostSession`'s pipe read had no timeout at all.** With the proactive reroute above correctly routing Edge to the subprocess, a run was observed where the child sat alive and unchanging for 95+ seconds with *no* `msedgewebview2.exe` helper process ever spawned (i.e. stuck somewhere in the pipe handshake itself, not in WebView2) — and the parent's plain synchronous `_pipe.Read()`, having no timeout, blocked right along with it. **A subprocess only actually delivers isolation if the caller can also give up on it** — a parent blocked forever waiting on a child is no better off than if it had attempted the risky operation itself. Fixed: `PersistentEncConverterHostSession.ReceiveOneMessage` now uses `_pipe.ReadAsync(...).Wait(TimeSpan)` bounded by a new `ReceiveTimeoutSeconds` (30s — comfortably longer than `WebBrowserEdge`'s own 20s internal timeout, so a *normal* WebView2 timeout-and-crash cycle inside the child has time to occur without the parent giving up first) and, on timeout, force-kills the child (`KillProcessBestEffort` — `HostProcessJobObject`'s kill-on-close job only covers an uncleanly-*killed parent*, it's not a substitute for the parent reclaiming a child it's deliberately giving up on) before throwing a `TimeoutException`, which `Convert()`'s existing catch-and-retry-once logic now also recognizes.

**Final, verified end state**: `TestTechHindiSiteConverter(...;Edge)` now fails in a clean, bounded, fully-catchable way — `System.TimeoutException: EncConverterHostExe did not respond within 30s` after ~63s (one failed attempt plus one retry, per the existing retry-once policy) — instead of hanging the test host indefinitely or crashing it via the native window-class error. Every other `TechHindiSiteEncConverter` spec (both `InternetExplorer`-resolving cases) passes, including the one that surfaced the `ConversionType` staleness bug. Full `TestEncCnvtrs` suite re-run clean twice in a row on `net9.0-windows`/x64 (110/142 passing both times, identical failure set both runs: 12 AI-translator tests needing live credentials/network/a local NLLB server, 8 pre-existing ICU `Iso8859` mojibake failures, 1 test needing an x64 Python interpreter not installed on this dev machine, and the one Edge `TimeoutException` above — none caused by this pass's changes). One transient, non-reproducing native access-violation crash inside unrelated `TecEncConverter`/TECkit code was observed once across ~4 full-suite runs and did not recur on immediate retry — treated as environmental flake (likely related to how hard this dev machine's native-process infrastructure has been exercised this session), not a regression, but worth a note in case it recurs for someone else.

**What this does *not* fix, and shouldn't be expected to**: the underlying WebView2 native hang itself. Nothing found this pass explains *why* `CreateCoreWebView2Controller` gets stuck in the first place on this environment (and, per the project owner's report, the clean VM too) — only that once it does, no amount of managed-code timeout/cancellation/`Dispose()` can safely recover the *same process* from it. The fix here is containment (never let the real host process be the one holding this bag when a subprocess route exists), not a cure. **Practical implication**: this containment only actually protects Word/Paratext/any real host when `SILConverters`'s `InstallDir` is genuinely configured on that machine (see `EncConverters.IsSubprocessFallbackAvailable`) — on a bare dev/test box or a Paratext-only install with no `InstallDir` key, `WillUseEdgeBrowser`'s proactive check finds nothing to route to and falls through to today's in-process attempt, same as before this pass (degrade-gracefully, consistent with every other check in this feature). If the hang recurs specifically in a host process with no `InstallDir` configured, it will still hang/crash exactly as it did before this investigation — that gap is real and by design (matching the same graceful-degradation stance the rest of this feature already takes), not an oversight.

**Decision: Edge support is being shelved, not fixed. `UseEdge` is being set to `False` in the field, falling back to the `InternetExplorer` engine, which works reliably.** Before abandoning it, one more real clean-VM test narrowed the failure further and is worth recording, since it rules out both leading theories above:

- Tested with a *real* SILConverters-installer deployment on the clean VM (not the hand-copied folder from the manual-test steps above) — `EncConverterHostExe.exe`/`.exe.config`, `ECInterfaces.dll`, `Newtonsoft.Json.dll`, `SilIndicEncConverters40.dll`, `SilEncConverters40.dll`/`.dll.config`, `Microsoft.Web.WebView2.Wpf.dll`/`.Core.dll`/`.WinForms.dll`, and `WebView2Loader.dll` all present and current in `InstallDir` (`C:\Program Files\SIL\SILConverters`), `InstallDir` correctly registered. The registry cache marker confirmed the subprocess fallback genuinely engaged. **Same failure anyway** — ruling out the "manual test deployment was missing files" theory from earlier in this investigation.
- The actual error surfaced this time (previously masked by the pipe-timeout/crash noise) is far more specific than "WebView2 runtime doesn't match the SDK": `System.InvalidCastException: Unable to cast COM object of type 'System.__ComObject' to interface type 'Microsoft.Web.WebView2.Core.Raw.ICoreWebView2Environment'... QueryInterface call ... for the interface with IID {B96D755E-0319-4E92-A296-23436F46A1FC} failed ... (Exception from HRESULT: 0x80004002 (E_NOINTERFACE))`. This is the *original* bug this whole feature was built around (`Unable to cast to ICoreWebView2Environment`) — reproducing **inside the fully isolated subprocess, with nothing else loaded**. That rules out the theory the entire feature was designed against (a host process's own resident `WebView2Loader.dll` winning the DLL-search-order race) — there's no host process, no competing copy, nothing to lose that race against here. Whatever this is, it isn't a DLL-search-order collision.
- **Genuinely odd, unresolved data point**: opening the same `.html` file directly in the Edge *browser* and driving the conversion by hand through the page's own input box works fine. This doesn't actually confirm the embedding path should also work, though — the full Edge browser (`msedge.exe`) and the separately-installed "WebView2 Runtime" (Evergreen) used for embedding are different products that merely share code lineage and usually track close version numbers; a machine can have a healthy, current browser while the Runtime `WebView2Loader.dll` actually resolves via COM activation is a different, mismatched build (there can be more than one WebView2 Runtime registration on one machine — per-machine and per-user, sometimes stray copies pulled in by other installed apps — and `WebView2Loader.dll`'s own discovery precedence picks whichever it finds first, not necessarily the one whose version was checked in the registry). This was **not tested further** — next step, if this is ever revisited, would be checking for multiple WebView2 Runtime registrations (`reg query HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients /s /f "{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}"` and the per-user equivalent under `HKCU`) rather than trusting a single version check.
- **Net effect**: the QueryInterface failure appears to be a genuine SDK/Runtime ABI incompatibility specific to this class of environment, independent of process isolation, and not something this session's containment work was ever going to fix (it was designed for a different failure category). The containment work (proactive subprocess routing, the STA fix, the bounded pipe timeout, the handshake fix) all remain correct and worth keeping regardless — they're what turned an indefinite hang/host-process crash into a clean, fast, catchable failure, which is what made this specific error message visible at all instead of being masked by a timeout or a native crash. They just don't make Edge actually work here.

## The VS 2022 / VS 2026 / WiX blocker

There's a toolchain constraint that isn't really about this repo's code at all, but blocks how modernization work can proceed in practice: the installer projects (`installer/*.wixproj`) are built against WiX Toolset **v3.14.1**, which uses the old Votive-style Visual Studio integration and is only realistically usable inside **VS 2022**. VS 2026 doesn't support that integration, but VS 2026 is what's needed to comfortably target `.NET 10.0` (per the `CLAUDE.md` framework matrix) day-to-day in the IDE — so right now, the WiX dependency is what's forcing a split between two versions of Visual Studio.

The current WiX major version is **v7.0.0** (v6 is the prior stable line; both are still supported by FireGiant, WiX's steward). Since **v4**, WiX authoring moved to SDK-style `.wixproj` projects (a `Sdk="WixToolset.Sdk"` reference resolved via NuGet, the same pattern as SDK-style `.csproj`), which build via plain MSBuild/`dotnet build` and do **not** require a special VS integration extension to be installed at all — merge modules (`.msm`, used throughout `installer/`) remain supported. Note, though: FireGiant has explicitly declined ("closed as not planned") to make the HeatWave VS-integration extension (IntelliSense/wizards for authoring `.wxs` files) work with VS 2026 — so upgrading WiX gets you a build that works in VS 2026, not full in-IDE authoring tooling there.

**Recommendation: do the WiX v3.14.1 → v6/v7 migration before (or as the first slice of) the broader SDK-style C# conversion**, not after:
- It's the same category of change — SDK-style project conversion — just scoped to the ~13 `.wixproj` files in `installer/` instead of the ~20 C#/C++ projects in `src/`. Doing it first validates the SDK-style approach on a smaller, self-contained surface before the bigger conversion.
- It directly removes the reason you're stuck in VS 2022. Once the installer no longer needs Votive/HeatWave to build, there's nothing forcing a return to VS 2022 for anything, and the rest of the modernization (SDK-style `.csproj`, `net9.0`/`net9.0-windows` multi-targeting) can be done entirely inside VS 2026 instead of split across two IDEs.
- **Caveat, corrected:** these `.wxs` files don't use directory/project auto-harvesting — every component is hand-authored exactly, so the known auto-converter harvesting bug (it can strip a harvested `ComponentGroupRef` without replacing it) doesn't apply here. The real content of these files, and the thing that actually matters, is that they hand-author **COM class registration** — `Class`/`ProgId`/`TypeLib`/`Interface`/`Registry` entries baked directly into the MSI, rather than relying on runtime self-registration (`regasm`/`RegisterForComInterop`) during install. That's the correct, standard approach: Windows Installer can't reliably roll back or repair arbitrary self-registration code run as an install action, so the exact registry state a COM class needs gets authored once and owned by MSI like any other installed resource, the same way it's done today. Those elements are unchanged in purpose and still present in the current WiX v4–v7 schema, so this isn't blocked by the upgrade — the mechanical cost is the XML namespace change (v3's `schemas.microsoft.com/wix/2006/wi` → v4+'s `wixtoolset.org/schemas/v4/wxs`), which `wix convert` handles well for this kind of fixed, non-harvested content. **Given real external consumers depend on this working (see the Discovery mechanism item below), verify — don't just build-test:** after conversion, install the new MSI on a clean machine and `reg export` the resulting `Class`/`ProgId`/`TypeLib`/`CLSID` keys, diffing against what the current v3.14.1-built installer produces, to catch anything the schema migration silently changed (a build success doesn't guarantee byte-for-byte-equivalent registration).

## In-situ modernization vs. new project

The repo owner is weighing whether to modernize this codebase in place or start fresh under a new `SIL.Transduction`-branded project. Framing the tradeoff:

**In-situ modernization** (incremental, keeps history and existing client compatibility)
- Lower risk to existing consumers (Paratext, FieldWorks, etc.) — no "flag day" cutover.
- Can be done in stages, each independently shippable.
- Carries forward 20 years of accumulated legacy (non-SDK projects, COM self-registration, the browser-engine sprawl, dormant code like `ConvertersActivator`) — modernization work is partly "renovation," not just "add SDK-style project files."
- The native/COM core (`IEncConverter`, CC/TECkit/ICU wrappers) has no real reason to be rewritten — it works, it's stable, and it's exactly the part that's expensive to redo. A rewrite would spend most of its effort re-solving already-solved problems.

**New project** (clean slate under `SIL.Transduction`)
- Freedom to design the interface and packaging correctly the first time (e.g. no COM/registry coupling, proper SDK-style multi-targeting from day one).
- Existing client apps would need a compatibility shim or a migration project of their own — this cost is easy to underestimate given how many consumers exist (Paratext, FieldWorks, MS Office/LibreOffice plugins, in-house tools).
- The legacy native transducers (CC, TECkit, ICU, Python) would still need to be ported or wrapped somehow — "new project" doesn't remove that work, it just relocates it.

**Recommendation:** in-situ, project-by-project. The core interface and native transducers are stable assets, not liabilities — the actual pain (non-SDK projects, COM/registry discovery, browser sprawl) is fixable incrementally without a rewrite, and a rewrite would put the actively-useful `EcTranslators` work on hold while re-deriving things that already work. A namespace move to `SIL.Transduction` can happen incrementally too (type-forward or alias the old namespace) rather than requiring a new repo.

## Suggested phased roadmap

Mapped to the constraints already set in `CLAUDE.md` (target framework matrix: `net462`/`net48` for legacy boundaries, `netstandard2.0` where UI-free, `net9.0`/`net9.0-windows` with modern UI abstractions; SDK-style C# projects; standard MSBuild C++ projects; `SIL.Transduction` namespace target):

1. **WiX v3.14.1 → v6/v7 migration.** Do this first (see above) — it's a smaller, self-contained SDK-style conversion that unblocks moving off VS 2022 entirely, before starting the larger C# conversion below.
2. **SDK-style conversion, UI-free projects first.** `ECInterfaces`, `EncCnvtrs`'s non-UI pieces, and the transducer wrapper assemblies that don't touch `WebBrowserAdaptor` are the easiest SDK-style/multi-target candidates (`net462;net48;netstandard2.0`). This is mechanical and low-risk, and unblocks everything else.
3. **Browser engine consolidation.** `AutoConfigDialog`'s "About" tab (the only browser-engine consumer shared by every transducer's Setup dialog) has already been switched to launching the OS default browser instead of embedding one (see "The browser-engine problem" above) — done, not just planned. The GeckoFX NuGet packages and the `Firefox`/`Firefox64` binary payload/merge modules are also already gone — done, not just planned. What's left: settle the Linux question for the one remaining consumer, `TechHindiSiteEncConverter` (drives a live third-party website in-process, a different requirement than static docs) — Linux currently has no working embedded-browser option at all now that GeckoFX is gone, only a misleading "install Edge" instructional message — then decide `WebBrowserAdaptor`'s final shape: WebView2 on Windows, and a decided-upon answer for Linux (or "no Linux UI" for that one converter).
4. **Discovery mechanism — real external consumers confirmed, treat COM registration as a hard compatibility constraint.** Two separate things got conflated earlier in this doc and need un-conflating: the *mapping-registry XML file* (where named conversion mappings live, `ProgramData\SIL\Repository`) is indeed SIL-internal-only and safe to evolve freely. But **COM class registration for `SilEncConverters40.dll` itself is not** — there are confirmed real external (non-SIL) consumers, e.g. Word VBA/VBScript macros that `CreateObject()`/late-bind against its exposed ProgIDs directly, bypassing the `EncConverters` dispatcher entirely. That means the `Class`/`ProgId`/`TypeLib` registration for the core assembly's COM-visible types must keep working indefinitely via whatever mechanism (installer-authored registry entries, as today, or a future equivalent) — this is not a "nice to keep for now," it's a real backward-compatibility requirement for consumers this repo doesn't control and can't inventory. Individual transducer plugin DLLs are lower risk here since, per the project owner, only the core assembly's types are known to be consumed this way externally.
5. **Namespace migration to `SIL.Transduction`.** Do this after step 2 so it's a mechanical rename across already-modernized projects; use type-forwarding attributes or namespace aliases so existing compiled client apps referencing the old namespace/assembly names don't break immediately. Do the `AIGuesserEC`/`DriveAiEncConverter` → `AdaptIt*` rename (confirmed above) as part of this pass, or earlier if it's easy to slot in sooner.
6. **Linux/autotools build and `ConvertersActivator`: no action needed.** Both are confirmed dormant with the project owner's sign-off to leave as-is — don't spend modernization effort here. Revisit the Linux build only if the `net9.0`/`net9.0-windows` cross-platform targets make Linux support cheap enough to reconsider without Mono.
7. **`EcTranslators` keeps moving independently.** It's already on modern SDK-friendly NuGet packages (`Azure.AI.OpenAI`, `Google.Cloud.AIPlatform.V1`, etc., via the shared `SharedItems.props`) — it doesn't need to wait on the rest of the modernization and shouldn't be blocked by it.
8. **Net9-windows merge modules — probably needed eventually, not started.** The SDK-style conversion (step 2, now done — all ~19 C#/native projects multi-target `net462;net48;net9.0-windows` plus `netstandard2.0`/bare `net9.0` for the UI-free pieces, superseding the original `net462;net48;netstandard2.0` framing above) means every transducer/converter now has a real `net9.0-windows` build sitting in `output\net9.0-windows\...` alongside the `net48` one. The nuget package's `lib\` folder already ships both (see `Package.Release.nuspec`), and its `runtimes\EcDistFiles\` bundle is being extended similarly. But the `installer/*.wixproj` merge modules (`EC_40_MM`, `EcTranslatorsMM`, etc.) still only package the `net48` build. That's fine for `net462` consumers (same in-place-upgraded .NET Framework CLR family, no runtime isolation between them) but **not** for a `net9.0-windows` consumer — .NET Framework and .NET Core/.NET 9 are separate, non-interoperable runtimes, so a `net9.0-windows` client can't load the `net48`-built WinForms/COM-registered DLLs at all. The reason this matters (not just a nuget-package nicety): `SilConverters` (sister repo, `..\silconverters`) and other client installers are meant to consume these merge modules directly rather than harvesting a folder of DLLs/EXEs by hand — that's the whole point of authoring them. If/when a client installer needs to target a `net9.0-windows` host app, it'll need genuinely new merge modules built from the `net9.0-windows` output, not a reuse of the existing `net48`-targeted ones — and unlike the old pattern (single DLL + `.tlb` + hand-authored COM registry entries), a `net9.0-windows` merge module would likely need to bundle each assembly's `.deps.json`/`.runtimeconfig.json` and a much larger dependency-package closure, and probably drop classic COM self-registration entirely (.NET Core doesn't do it the same way .NET Framework does). Not started — flagging so whoever picks up client-installer work for a modern-.NET host knows this gap exists before assuming the existing merge modules are TFM-agnostic.
